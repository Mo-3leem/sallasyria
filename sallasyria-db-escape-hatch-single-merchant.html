Moving One Merchant to Its Own Database

The Option A verdict already promises this: if one merchant ever grows exceptionally large, or a contract demands a private database, that one store can be lifted out of the shared SQLite file and into its own — without rebuilding anything. This appendix is the exact mechanism.

1

Why It Works Without Rebuilding Anything

The shared schema was already built for this exit, three properties do all the work:

  • store_id on every store-owned table. All 11 non-platform tables (subscriptions, categories, products, product_images, customers, customer_addresses, shipping_rates, orders, order_items) already carry store_id. A single merchant's full dataset is therefore a closed set of WHERE store_id = ? rows — no query needs to change to select "everything one merchant owns."
  • Composite FKs already scope every child-of-child link to the same store. Every cross-table reference below stores is FOREIGN KEY (store_id, ref_id) REFERENCES parent(store_id, id), backed by a UNIQUE(store_id, id) key on the parent. Because the FK itself is store-scoped, a row copied out of the shared DB can never accidentally resolve against a different store's parent row on the target — the constraint that protects tenant isolation on the shared DB is the same constraint that guarantees a clean, closed copy on the isolated DB.
  • Snapshots make orders self-contained. orders and order_items carry their buyer, delivery and price fields as snapshots taken at purchase time. Moving a store's orders never depends on also having a live, unmodified copy of customers or products in perfect sync — history is already frozen inside the order rows themselves.

Net effect: isolating a merchant is a data-copy operation, not a schema change. The target database is created from the exact same CREATE TABLE / index / trigger DDL as the shared database (see structure doc, section 3) — same 12 tables, same columns, same constraints, same UUIDs preserved on copy. Nothing is renamed, added, or restructured.

2

Copy Order — Parent → Child

Run against an ATTACHed target database with PRAGMA foreign_keys = OFF for the duration of the copy (re-enable and verify per section 3 immediately after). Every statement preserves the source id — no regeneration, so every composite FK still resolves identically on the target. 

-- one merchant's store_id, fixed for the whole run
-- :sid = the store's id, :oid = that store's owner_id (stores.owner_id)

-- 0. target file, same DDL as the shared database (section 3 of the structure doc)
ATTACH DATABASE 'store_<slug>.db' AS target;
PRAGMA foreign_keys = OFF;

-- 1. users — only the owning row (subscriptions/orders/etc. never reference
--    users directly, but stores.owner_id does, and the FK is ON DELETE RESTRICT
--    so the owner row must exist on the target before stores is copied)
INSERT INTO target.users
SELECT * FROM main.users
WHERE id = (SELECT owner_id FROM main.stores WHERE id = :sid);

-- 2. plans — every plan this store's subscription history has ever used
--    (plans is platform-wide and has no store_id; copy only rows actually
--    referenced by this store's subscriptions, not the whole table)
INSERT INTO target.plans
SELECT * FROM main.plans
WHERE id IN (
  SELECT DISTINCT plan_id FROM main.subscriptions WHERE store_id = :sid
);

-- 3. stores — the tenant row itself, order_counter carried over as-is so
--    numbering continues from exactly where it left off, no reset
INSERT INTO target.stores
SELECT * FROM main.stores WHERE id = :sid;

-- 4. subscriptions — full billing history, active + cancelled + expired,
--    not just the current period
INSERT INTO target.subscriptions
SELECT * FROM main.subscriptions WHERE store_id = :sid;

-- 5. categories — parent rows before child rows if you enforce order
--    manually; FK is deferred-safe here since foreign_keys is OFF, so one
--    statement is enough regardless of self-referencing parent_id order
INSERT INTO target.categories
SELECT * FROM main.categories WHERE store_id = :sid;

-- 6. products
INSERT INTO target.products
SELECT * FROM main.products WHERE store_id = :sid;

-- 7. product_images
INSERT INTO target.product_images
SELECT * FROM main.product_images WHERE store_id = :sid;

-- 8. customers
INSERT INTO target.customers
SELECT * FROM main.customers WHERE store_id = :sid;

-- 9. customer_addresses
INSERT INTO target.customer_addresses
SELECT * FROM main.customer_addresses WHERE store_id = :sid;

-- 10. shipping_rates
INSERT INTO target.shipping_rates
SELECT * FROM main.shipping_rates WHERE store_id = :sid;

-- 11. orders — snapshot fields travel with the row untouched
INSERT INTO target.orders
SELECT * FROM main.orders WHERE store_id = :sid;

-- 12. order_items — last, since it references both orders and products
INSERT INTO target.order_items
SELECT * FROM main.order_items WHERE store_id = :sid;

PRAGMA foreign_keys = ON;

12 statements for 12 tables  ·  users and plans are filtered to only the rows this store actually needs, never copied in full  ·  all UUIDs/ULIDs preserved verbatim  ·  source rows are left untouched by this step — deletion from the shared DB happens only after verification and cutover (section 5)

3

Verification SQL

Per-table row count match — run once against main (shared) and once against target (isolated), diff the two result sets:

SELECT 'users'               AS tbl, COUNT(*) FROM users               WHERE id = :oid
UNION ALL SELECT 'plans',            COUNT(*) FROM plans               WHERE id IN (SELECT DISTINCT plan_id FROM subscriptions WHERE store_id = :sid)
UNION ALL SELECT 'stores',           COUNT(*) FROM stores              WHERE id = :sid
UNION ALL SELECT 'subscriptions',    COUNT(*) FROM subscriptions       WHERE store_id = :sid
UNION ALL SELECT 'categories',       COUNT(*) FROM categories          WHERE store_id = :sid
UNION ALL SELECT 'products',         COUNT(*) FROM products            WHERE store_id = :sid
UNION ALL SELECT 'product_images',   COUNT(*) FROM product_images      WHERE store_id = :sid
UNION ALL SELECT 'customers',        COUNT(*) FROM customers           WHERE store_id = :sid
UNION ALL SELECT 'customer_addresses', COUNT(*) FROM customer_addresses WHERE store_id = :sid
UNION ALL SELECT 'shipping_rates',   COUNT(*) FROM shipping_rates      WHERE store_id = :sid
UNION ALL SELECT 'orders',           COUNT(*) FROM orders              WHERE store_id = :sid
UNION ALL SELECT 'order_items',      COUNT(*) FROM order_items         WHERE store_id = :sid;

Run this identical query against main and target; every row of the two 12-row result sets must match exactly. Any mismatch blocks cutover.

Referential integrity on the target — must return zero rows:

PRAGMA foreign_keys = ON;
PRAGMA foreign_key_check;

A non-empty result means a copied child row points at a parent that either wasn't copied or lost its store_id match — most likely a missed plans or users row. Fix the missing parent row and re-run; do not proceed to cutover while this returns anything.

Spot-check the two preserved invariants:

-- order_counter carried over exactly, not reset to 1000
SELECT order_counter FROM target.stores WHERE id = :sid;
-- must equal:
SELECT order_counter FROM main.stores WHERE id = :sid;

-- order_number sequence still gapless and unique per store on the target
SELECT COUNT(*), COUNT(DISTINCT order_number) FROM target.orders WHERE store_id = :sid;
-- the two counts must be equal (no duplicate order_number values)
4

App Routing — store_id → DB File Factory

The Connection Contract (structure doc, section 3) already centralizes every connection behind one factory. The escape hatch adds exactly one responsibility to that factory and touches nothing else in the app: 

function getConnection(store_id) {
  const dbPath = storeDbOverrides.has(store_id)
    ? storeDbOverrides.get(store_id)   // e.g. 'store_<slug>.db'
    : SHARED_DB_PATH;                  // default for every other store

  const conn = open(dbPath);
  conn.exec('PRAGMA foreign_keys = ON');
  conn.exec('PRAGMA busy_timeout = 5000');
  return conn;
}

storeDbOverrides is a small store_id → file-path lookup (table, config row, or env-driven map)  ·  default remains the one shared SQLite file for every store not in the map

Every call site already asks the factory for a connection and already carries store_id on the request (that's the tenancy model). No handler, query, migration, or repository class changes: they still filter by store_id exactly as before, they simply now run against whichever file the factory handed back for that store. Isolating a second or third merchant later is only another entry in the same map — still no code change beyond the factory added once.

5

Cutover

1. PauseBlock new writes for this store_id only — reject or queue checkout/admin writes at the app layer for that store while every other store keeps writing to the shared DB uninterrupted.
2. Final syncRe-run the section 2 copy for this store_id to catch any row written between the first copy and the pause, then re-run every check in section 3 until all counts match and both PRAGMA checks are clean.
3. SwitchAdd store_id to storeDbOverrides so the connection factory starts returning the isolated file. No deploy of app code, no schema migration — one config/map change.
4. UnpauseResume writes for this store; they now land in the isolated database through the same store_id-filtered code paths.
5. Rollback windowKeep the store's rows in the shared database untouched and read-only (do not delete) for an agreed window. If anything is wrong post-cutover, remove the storeDbOverrides entry to route the store back to the shared DB with zero data loss. Only after the window closes clean, delete the store's rows from the shared database.

Nothing else changes. Default remains one shared SQLite database for every store. This procedure is dormant until a specific store_id is added to the override map — no new tables, no renamed tables, no schema drift between the shared DB and any isolated DB it ever produces.
