Database Architecture Overview

Salla Syria is a multi-tenant e-commerce SaaS platform. Merchants sign up, create their own online stores, and sell to their own customers — all running on one shared system.

The platform uses a single shared Cloudflare D1 database (SQLite-compatible). Every store’s data is kept separate by a store identifier (store_id) carried on every store-owned table, so one merchant can never see or affect another merchant’s data.

Platform users sign in to create and manage their stores, and platform administrators oversee all stores from the same system. Each store then owns its own product catalog, customer list, orders, and delivery pricing — fully independent of every other store on the platform.

Main Entities

Platform & Store

usersPlatform accounts for store owners and platform administrators — name, required unique phone as contact identity, email as the login identity (required and normalized at the app layer), an email-verified flag that login requires, role, and active status.
storesAn individual online store — the tenant, with its owner, web address, currency, status, and its own order-number counter.
plansThe subscription plans the platform offers to merchants, with monthly and yearly pricing and included limits.
subscriptionsA store’s plan and billing period, with status, start date, end date, cancellation date, and payment reference. Earlier periods are kept as history, and only one subscription per store may be active at a time.

Authentication & Idempotency

sessionsServer-side login sessions — one row per opaque token (SHA-256 hash only, never the raw token), with expiry, revocation and idle-timeout timestamps. User-scoped, never store-scoped.
email_tokensSingle-use email tokens for verification and password reset — hashed, expiring, consumed atomically so concurrent redemptions collapse to one winner.
idempotency_keysExactly-once checkout claims — primary key (store_id, key), so key strings are independent per store; each claim carries its order and a hash of the request body.

Catalog

categoriesHow a store organises its products for browsing — name, web address, optional parent category, and display order.
productsThe items a store sells, with price, stock, and availability. Removed products are retired with a deletion date rather than erased.
product_imagesThe product photo gallery, shown in a set display order. Carries its own store reference and is retired by the same soft-deletion rule as products.

Customers

customersThe buyers of one store, recorded at checkout by name, phone, and optional email. No buyer login in this release.
customer_addressesSaved delivery addresses so returning buyers do not retype them — store reference, recipient, phone, governorate, city, address, and a default flag.

Orders & Fulfillment

shipping_ratesA store’s delivery method and cost for each Syrian governorate, unique per governorate within the store.
ordersA placed order: store, order number, customer, order progress, payment state, payment reference, totals, tracking number, plus buyer name*, buyer phone*, delivery method*, delivery cost*, delivery governorate* and delivery address*.
order_itemsThe purchased lines: store, order, quantity, plus product name*, chosen options*, unit price* and line total*.

* Snapshot fields. These values are copied into the order at the moment of purchase and are never changed afterwards. If a product is later renamed, repriced or retired — or a customer updates their phone number or address — every past order still shows exactly what was bought, at what price, and where it was delivered.

PK = primary key  ·  FK = foreign key  ·  UK = unique  ·  money held as whole numbers in minor units  ·  composite UNIQUE and partial-index rules are stated on the column they apply to but are implemented as separate CREATE UNIQUE INDEX statements, not inline column constraints  ·  every child-of-child foreign key is a composite FOREIGN KEY (store_id, ref_id) REFERENCES parent(store_id, id) backed by a UNIQUE(store_id, id) key on the parent, so a child row can never reference a parent belonging to a different store  ·  D1 enforces foreign keys natively with no per-connection PRAGMA

Enforcement DDL. GOVERNORATES = ('Damascus','Rif Dimashq','Aleppo', 'Homs','Hama','Latakia','Idlib','Al-Hasakah','Deir ez-Zor','Raqqa','Daraa', 'As-Suwayda','Quneitra','Tartus') — CHECK(governorate IN GOVERNORATES) applies to customer_addresses.governorate, shipping_rates.governorate and orders.shipping_governorate. Composite foreign keys take the form FOREIGN KEY (store_id, ref_id) REFERENCES parent(store_id, id), backed by UNIQUE(store_id, id) on the parent. Partial-unique rules are separate statements: CREATE UNIQUE INDEX uq_subscriptions_store_active ON subscriptions(store_id) WHERE status = 'active'; CREATE UNIQUE INDEX uq_addresses_customer_default ON customer_addresses(customer_id) WHERE is_default = 1. subscriptions.cancelled_at carries CHECK((status = 'cancelled' AND cancelled_at IS NOT NULL) OR (status != 'cancelled' AND cancelled_at IS NULL)). Token hashes are globally unique: CREATE UNIQUE INDEX uq_sessions_token_hash ON sessions(token_hash); CREATE UNIQUE INDEX uq_email_tokens_hash ON email_tokens(token_hash). Checkout idempotency keys are scoped per store by PRIMARY KEY (store_id, key) since migration 0007, so the same key string in two stores never collides.

Required indexes. SQLite does not auto-index foreign key columns, so the following plain (non-unique) indexes are required besides the UNIQUE constraints above: stores(owner_id), subscriptions(plan_id), subscriptions(store_id), categories(store_id, parent_id), products(store_id, category_id), products(store_id, is_active, deleted_at), product_images(store_id, product_id, sort_order), customer_addresses(store_id, customer_id), orders(store_id, customer_id), orders(store_id, status), orders(store_id, created_at), order_items(store_id, order_id), sessions(user_id), idempotency_keys(store_id, created_at), email_tokens(user_id, purpose).

Checkout Transaction Contract (D1). Rules for the Hono checkout handler: (1) stock decrements, counter increment (UPDATE stores SET order_counter = order_counter + 1 WHERE id = ? RETURNING order_counter), customer upsert, order insert, all order-item inserts and the idempotency-key claim go in ONE single env.DB.batch() call — D1 executes the batch in one implicit transaction, so a later failure rolls back every statement including the counter bump and order numbers are never skipped; (2) upsert the customer with INSERT ... ON CONFLICT(store_id, phone) DO UPDATE rather than check-then-insert, so a concurrent double-submit resolves atomically instead of surfacing a constraint error to the buyer; (3) compute every order_items.line_total as quantity * unit_price and orders.total as subtotal - discount + shipping_cost in the same transaction, since the database cannot check totals across the orders/order_items boundary. (4) No BEGIN IMMEDIATE, no PRAGMA busy_timeout and no SQLITE_BUSY retry loop anywhere in this contract — env.DB.batch() is D1's own transactional primitive and supersedes that part of the original document entirely on D1.

Connection Contract (D1). D1 enforces foreign keys natively — no PRAGMA foreign_keys statement is used or needed. All ids are TEXT, generated in application code as UUIDv7/ULID; the database never generates ids. updated_at is application-managed by the Hono layer (no AFTER UPDATE triggers on D1); created_at and the initial updated_at value still default via strftime('%Y-%m-%dT%H:%M:%SZ','now') on INSERT.

Key Relationships

User → StoreA user can own one or more stores. A user with stores cannot be removed.
Store → ProductsEach store has its own products; products never cross stores.
Store → CategoriesEach store defines its own categories.
Category → ProductsA product may sit in one category, or none. A category with products or child categories cannot be removed until the application re-assigns them first; deleting a category never nulls anything out.
Product → Product ImagesA product has many images in a set display order; each image also carries its store reference.
Store → CustomersCustomers belong to a single store — the merchant owns their customer list.
Customer → AddressesA customer can have several saved delivery addresses; each address also carries its store reference.
Store → Shipping RatesEach store sets its own delivery method and cost per governorate, one rate per governorate.
Store → OrdersEvery order belongs to exactly one store, and order numbers run in sequence within that store.
Customer → OrdersEvery order is linked to the customer who placed it. A customer with orders cannot be removed.
Order → Order ItemsAn order contains one or more purchased lines; removing an order removes its lines.
Store → Order ItemsEach purchased line also carries its store reference, so order data can never cross stores.
Product → Order ItemsAn order line points back to the product, but keeps its own copy of the details, so retiring a product leaves past orders unchanged.
Store → SubscriptionA store has one active subscription at a time, with earlier periods kept as history.
Plan → SubscriptionEach subscription is based on one of the platform’s plans. A plan in use cannot be removed.
User → SessionsEach login mints one session row holding only the token hash; logout revokes, expiry and idle timeout are enforced by application queries. Removing a user removes their sessions.
User → Email tokensVerification and password-reset tokens belong to one user and are consumed exactly once; removing a user removes their tokens.
Store & Order → Idempotency KeysEach checkout claims one key per store; replaying the same key with the same body returns the stored order instead of creating a new one.

Important Design Decisions

Multi-Tenancy

A store identifier on every store-owned table isolates each store’s data — including product images, customer addresses and order lines. One database, many stores, no cross-store visibility.

Order Snapshots

Orders and order items keep their own copy of the buyer, delivery and price details as they were at the moment of purchase, so past orders stay correct even after products are renamed, repriced, or retired.

Order Numbering

Each store issues its own customer-facing order numbers from a counter held on the store, and the pair of store and order number is unique. Numbers stay sequential per store. The counter must always be incremented atomically with UPDATE stores SET order_counter = order_counter + 1 WHERE id = ? RETURNING order_counter inside the checkout write transaction — a separate SELECT followed by UPDATE is never allowed, otherwise two simultaneous checkouts can read the same value and collide.

Order & Payment State

The order carries two independent state fields: order progress and payment state. They move separately — a cash-on-delivery order can be delivered and paid, or shipped and still unpaid — and neither duplicates the other.

Payment

Payment method, payment state and payment reference are held inside the order itself rather than as a separate payment system — enough to support cash on delivery, bank transfer, and Syrian digital wallets.

Shipping

Delivery method and cost are held per governorate for each store, while the order keeps a snapshot of the method, cost, governorate and address the customer actually used.

Customer Handling

Buyers are recorded at checkout by phone number, with no account or password in this release. Every order is tied to a customer, so each store always has a complete customer list.

Soft Deletion

Products and product images are retired with a deletion date instead of being erased, so historical orders and reporting stay intact. A retired product releases its web address for reuse.

Idempotency

Each checkout claims its idempotency key inside the same batch as the order, keyed per store by PRIMARY KEY (store_id, key) — the same key string in two stores never collides, and replaying the same key with the same body returns the stored order instead of charging twice.

Email verification

Email is the login identity and login requires a verified address (403 until verified). Verification and password-reset tokens are stored hashed, expire, and are consumed atomically so concurrent redemptions collapse to one winner; email delivery itself never fails a business operation.

Lightweight MVP

The design is limited to the fifteen tables needed for the core selling flow, keeping the first release small, quick to build, and straightforward to extend later.

SQLite

SQLite fits an MVP of this size: the structure is lightweight, the operating cost is near zero, and there is no separate database server to run or maintain.

Data & Consistency Rules

  • IdentifiersGlobally unique text identifiers on every record.
  • MoneyWhole numbers in minor units — never decimals.
  • TimestampsEvery table records a creation timestamp, always in UTC, defaulting via strftime on INSERT; every table except idempotency_keys also records an update timestamp. SQLite defaults fire on INSERT only, and there are no AFTER UPDATE triggers on D1 — updated_at is written by the application on every update instead.
  • Foreign keysD1 enforces foreign keys natively with no per-connection PRAGMA; every relationship states explicit delete and update behaviour.
  • Foreign keysEvery relationship states explicit delete and update behaviour, enforced by the database.
  • ValidationStatus, payment, quantity and money fields are constrained to valid values.
  • Order historyPreserved as snapshots on the order and its lines.
  • Order numbersUnique per store, issued from the store’s counter — never globally unique.
  • Soft deletionProducts and product images are retired, never erased.
  • OrdersNever deleted; stores and customers with orders cannot be removed.
  • Tenant isolationEnforced through the store identifier on every store-owned table.
  • Store-scoped uniquenessProduct and category addresses, customer phone numbers, governorate rates and order numbers are unique within each store.
  • SubscriptionsOnly one active subscription per store; earlier periods kept as history.
